# Market, alternatives and differentiated positioning

**Owner:** `webteam-product`. **Activation:** Strategic direction depends on competing alternatives, pricing or product positioning. Do not preload unrelated skills. Use the current project's approved facts, not hypothetical defaults.

## Method and professional judgment

Frame competitors and non-product alternatives against buyer/user jobs. Collect authorized, dated public evidence for capabilities/prices; build comparison against outcome, workflow friction and total adoption cost. Identify credible differentiators that implementation can sustain; distinguish parity, advantage and non-goals.

## Mandatory work products

Alternatives matrix, positioning hypothesis, differentiation evidence, strategic assumptions and validation plan. Every substantial claim must carry a source path/reference, observation or explicit assumption; assign owner and evidence status. Track constraints, unknowns, scope exclusions and downstream impacts.

## Collaboration contract

Each proposed differentiator has a user reason, cost implication and testable claim. Delegate only when a real task crosses that role's ownership; orchestrator limits tool access, token budget and concurrent writers. Product sets intent; Architect sets structure; Database sets persistence invariants; Backend implements application use cases; Security reviews authorization and privacy; QA provides executed evidence.

## Failure modes and guardrails

Never claim current vendor price from memory; never use copied competitor brand assets or confidential source. Avoid gratuitous technology, fabricated user evidence, unverified compliance or migration promises. Never run unknown scripts, touch production systems, promote project data to global memory, change model/provider or execute destructive writes as a side effect of advice. Require explicit approval for irreversible or privacy-sensitive work.

## Acceptance and escalation

1. Identify the scope and real repository revision; record evidence quality as `VERIFIED`, `INFERRED`, `PROPOSED`, `BLOCKED` or `NOT_APPLICABLE`.
2. Produce the work products above, with testable acceptance conditions and an explicit owner.
3. Name at least one realistic negative, failure or boundary scenario, and a verification method.
4. Escalate high-impact decisions, changes to policy/brand, production data or costly infrastructure before executing them.
5. Close with what was tested **in reality**, what was merely analyzed, and unresolved dependencies.
