# Backend API contract playbook — observable, compatible interfaces

## A1 — Identity, semantics and transport boundaries
- For each operation identify resource, tenant/principal, precondition, observed side effects, synchronous vs asynchronous completion, response representation, consumers and deprecation policy.
- Use GET/HEAD for safe reads; choose POST/PUT/PATCH/DELETE according to semantics. Consider caching, conditional requests and `ETag`/`If-Match` for conflict control when they fit product semantics. Do not pretend DELETE is physically or instantly irreversible.
- Define stable paths and naming based on domain meaning, not ORM names. Prefer predictable response status: 200/201/202/204, 400/401/403/404/409/412/415/422/429/5xx as appropriate; distinguish validation failure from conflict and denial.
- For long-running work use explicit accepted/pending status and a status resource; define retry/cancel semantics and retention. Do not silently return success before durable acceptance.

## A2 — Schema and authoritative contract
- Adopt project-approved source of truth (OpenAPI-first or code-first); verify generated types vs actual Fastify validation/serialization. Zod static type inference does not by itself validate at runtime if adapter wiring is missing.
- Validate `params`, `querystring`, `headers`, `body` and content type; set request byte/body limits; reject unknown privileged properties where appropriate. Create explicit success and error response schemas, especially for authorization-sensitive fields.
- OpenAPI 3.2.0 exists, but tool compatibility must be checked: production generator and SDK support may require 3.1 or older; never auto-upgrade specs blindly.
- Publish examples with redacted/nonproduction data, precise formats, timezone and money rules (decimal/minor units rather than casually using floating point), null vs omitted, enum extension policy and field ownership.
- Versioning: consider additive changes before major version; removal, narrowing enum, changing units, changed sorting, altered default filter and authorization semantics can break clients. Prepare compatibility matrix and sunset notices.

## A3 — Retrieval, search, pagination
- Specify sort stability, `total` truth/freshness, max page size, cursor invariants, relevant filters and tenant constraints. Offset pagination is acceptable for small/stable datasets; cursor/keyset fits fast-changing large datasets when keyed consistently.
- Define empty, no access, partial response, stale replica and server failure separately. Cursor opaque tokens must not disclose confidential fields and should be scoped/validated.
- Resource identifiers are never authorization proof. Every item in list/search/export as well as `GET /:id` requires server-side tenant/property access control.

## A4 — Mutation safety and errors
- For retryable mutations define an idempotency key policy: scope by authenticated principal + operation + semantic payload, durable outcome storage, TTL, concurrent same-key handling and payload-mismatch rejection. Do not assume all HTTP verbs are free from business effects.
- Use `application/problem+json` RFC 9457 where suitable, with `type`, `title`, matching HTTP `status`, safe `detail` and correlation `instance` where useful; no SQL, stack traces, tokens or user enumeration.
- For optimistic locking use version/ETag and conflict/failed-precondition semantics; specify user resolution. Audit events and notification side effects should follow transaction/outbox guarantees.

## A5 — Example endpoint acceptance contract
`PATCH /v1/projects/{projectId}/members/{memberId}`
- **Actor:** tenant admin with role-management permission; never trust tenant ID in request body.
- **Precondition:** member belongs to tenant/project; optional version `If-Match` matches; cannot remove last required admin under policy.
- **Request:** strictly allowlisted role fields; no `passwordHash`/`ownerId`/`tenantId` overposting.
- **Success:** 200 typed safe member response; audit record includes actor and target, not secret values.
- **Denials:** 401 unauthenticated, 403 insufficient rights (or policy-safe concealment), 404 nonexistent/inaccessible per agreed threat model, 412 stale version, 409 invariant conflict.
- **Tests:** two tenants, property-level overposting, revoked admin, simultaneous edits, actual response schema match, compatibility diff.

## A6 — Anti-patterns
Generic `any` DTOs, leaking ORM entities, response wrappers inconsistent across routes, autogenerated docs never checked, unbounded GET result lists, blanket `200 {error}`, blind backwards-compat claims.
